# 周六双场景再演练：从人的写作过程审视 WriteField

> 2026-09-19。依据：四份主文档、Design README 与 HTML/CSS/交互源码、上一份双题演练，以及 Mosaic 当前本地文档和 Jump Palette 代码。
>
> 用户本轮重申的初衷：**帮助大家结合 AI 的强大能力，写出经过考量的文章，但又不会被 AI 完全掌控。**
>
> 性质：情境模拟与设计异议，全部方案为【待定建议】。不是实测用户行为，不是 S1 验收，不改变工程顺序。以下“我”的想法、对白、时间顺序均为助手构造，不能当作用户已经表达的偏好。
>
> 实际完成：核对资料；制作一份 Traversable 演练样稿与可运行例子；制作一份 Mosaic feature PRD 演练稿。浏览器安全策略禁止打开本地 HTML，未绕过；HTML 结论限于源码与交互路径审阅，没有声称视觉或 iPad 手感已验证。

## 一、这次与上一份演练不同在哪里

上一份 `saturday-dual-session-ai-audit.md` 很快接受了既有规则：没有段落就先打空标题，不知道该带什么就策展或刷新。这可以解释功能怎样用，却没有充分追问作者是否愿意这样写作。

本轮先模拟作者的认知变化，再判断产品是否接得住。不预设人已经有主题判断、段落、结构，也不把“生成了几张卡”当成进展。

初步判断：**现有设计擅长安放已经产生的内容，对帮助人形成判断、改变判断、把判断组织成文章，描述还薄。** 卡和连线可以继续作为表面，但不能反过来规定人的思考必须从一段正文开始。

“作者主导”至少包括：决定在问什么、看清依据、比较选项、拒绝建议、改变目标，以及决定怎么表达。最后按一次“插入”，只能保证正文写权限，不能单独保证这些能力。

## 二、场景 A：想写 Traversable，但不知道从哪里开始

### A1. 周六开题：我有兴趣，还没有论点

我打开空纸，题目暂写 `Traversable`。我不想让 AI 立刻交一篇从定义、定律到高级应用都齐全的教程，也不想先填写读者画像表。

模拟提问：

> 我想写 Traversable。我会用它，但讲的时候容易只复述类型签名。先和我找一个值得讲的问题，给两三个可能的切口，每个说清楚读者会因此明白什么。

AI 可以主动给具体材料：从批量解析切入、从形状与组合切入、从 laws 限制实例行为切入。随后问一个有帮助的问题：“你更想让读者会用它，还是纠正自己曾经误解它的地方？”不用固定访谈，不强迫每一步答题。

我选择“我会 fmap，为什么还要 traverse”，拒绝先讲 laws。**这次写作的方向是在对话中形成的，不是开写前已有的一项元数据。**

现有设计摩擦：AI 语义面 §2.2 / §四要求问题归属于文本锚点；§九建议空标题挂点。真正的空白没有可可靠匹配的引用文本，给空段造锚也没有回答“这段还不存在时，讨论属于什么”。

【待定建议】允许明确属于本篇的开题讨论，归属 Topic，段落锚点可稍后指定。入口可放在现有纸边 / 召唤入口，不必开全局聊天侧栏。关系诚实显示“关于这篇”，而不是伪装成第一段的旁注。范围仍是这篇文章，由作者发起；不是无目标的资料自动加工。

### A2. 连续追问：我不是在领取独立回答

模拟过程：

| 人的下一句话 | AI 应如何帮助 | 人形成的判断 |
| --- | --- | --- |
| 给一个足够小的例子 | 比较对文本列表使用 map 与 traverse | 从具体需求进入类型 |
| 所以它会收集全部错误？ | 指出要看所选 Applicative；用 Maybe 结果解释这个例子不能支持该概括 | 不把一个实例的行为写成整个 class 的定义 |
| 那是不是“把容器翻过来”？ | 给这个说法的适用范围与反例风险，回到签名解释 | 可用来入门，但不能停在口号 |
| 暂时不要 Tree，例子已经够了 | 记住这个取舍，停止自动扩写教学范围 | 我决定文章的负担与边界 |

前三个回答应当是同一问题下能继续读下去的讨论，而不是每次都摆一张同等权重的新卡。作者可以保留整个讨论，或把其中一句解释、一个反例、一个代码块另存为可引用的周边对象。

【待定建议】一张讨论卡容纳相关追问，分支或需要长期参照的材料再提出成卡。保留原问答来历，不用隐藏摘要替换原记录。AI 的能力可以强：举例、比较、解释、归纳都允许；是否保留、如何进入稿，由作者决定。

现有 `parentCardID` 与派生边能表达部分关系，但还没有交代“改口、追问、放弃上一轮解释”如何进入下一次请求。只把同段全部卡一并喂回，会把已经拒绝的解释也当成活跃建议。

### A3. 查证与小实验：我需要依据，不需要机器给真伪盖章

实际查阅了 [Data.Traversable 官方文档（base 4.15.0.0）](https://hackage.haskell.org/package/base-4.15.0.0/docs/Data-Traversable.html)，另写了 [可运行例子](simulations/traversable-example.hs)。本机 GHC 9.4.8 运行结果见该文件对应的文章样稿。

在模拟里，作者先预测输出，再对照运行结果，意识到“逐项得到解析结果”和“得到一个整体解析结果”是两个需求。这个过程会改变自己要写的句子，比多一个“最强反驳”菜单更重要。

产品应该让作者看清三层：原始文档说了什么、代码对这些输入实际输出什么、AI 对它们作了什么解释。来源可追踪不等于结论必然正确；URL 可访问也不能证明引文支持论断。

【待定建议】资料片段与 AI 解释可并看；对所选资料发起“比较 / 解释 / 归纳”时保留出处。外部工具结果可由作者带回为材料，并记录环境和输入。**此处不提议 WriteField 加本地 shell 或 iPad 代码执行器。** 为运行实验而离开应用是合理切换；要减少的是回来后重新找回写作位置与问题的成本。

当前 schema 只覆盖网页 provenance，对本地文件、代码位置、作者手写判断与实验输出的来历还不充分。断网也不应该把已有原文突然变成“模型自己说的”。这需要重新讨论来源建模，不能随手增加第四个枚举绕过既有约束。

### A4. 从理解到文字：我开始写，但会回头

演练样稿见 [从一组解析结果开始理解 Traversable](simulations/traversable-article.md)。它选择从两个需求的差异起笔，未把 AI 给出的全部知识点塞进去。

更自然的循环是：我写一段自己的解释 → 请 AI 按目标读者阅读 → AI 指出“组合效应”太抽象 → 我补一个例子 → 我删掉最初的“翻转容器”开场。

这里暴露两个缺口：

- **改写是日常，不是异常。** 现有锚点以引用文本重新匹配，原句改掉时可能失效。禁止猜测吸附是对的，但不能把每次认真修改都变成一次“维修卡片”。应区分应用内已知编辑引起的位置变化与重新载入后的不确定匹配；前者可以跟踪确定的编辑映射，后者有歧义才请人重挂。具体语义边界待定，不能偷偷改成相似度吸附。
- **一张卡会帮助不止一段。** 对 Maybe 的解释后来在结尾也有用。作者想暂时拿来对照，不想改它原本属于哪里，也不一定想把它永久放进所有后续 AI 请求。

【待定建议】分开“归属哪里”“暂时放在眼前”“本次让 AI 读”。提供临时留在旁边的参照方式，仍无第二台相机。临时参照不制造永久多重归属；真正多段引用另由作者建立明确关系。

### A5. 收尾与离开

模拟请求：

> 从头读这篇，按刚会 fmap 的读者看：哪里要求了我没解释的知识？开头的问题最后回答了吗？先给最重要的两点。

作者已经明确要求全文，产品不该先让他切 `full`、刷新包、再输入同一问题。授权读全文可以由这次请求表达，超出预算要显示缺了哪些部分。

离开时真正有用的便笺可能只有一句：“开头已有例子；回来决定要不要解释列表 Applicative，先别扩到 Tree。”这比机械恢复三张资料卡更接近恢复思路。可以自己写，也可以显式请 AI 提议，作者确认；不在关闭时偷偷调用模型。

开题方向卡以后没再打开，并不证明它没有价值：它已经帮助我决定怎么起笔。卡片也可以因改变理解、排除一条路而完成任务，不必全部“回填”。

## 三、场景 B：为 Mosaic 写一个新 feature 的 PRD

### B1. 先有一个问题，再有功能名

本轮不用上一份演练的 Recent/Pinned。选择假设 feature：**“下次从这里继续”——给现有 Note 一个 Room 接续指定，并可关联一个 tile。**

模拟出发点：“Mosaic 恢复了我昨天的工具，但我仍忘记自己下一步要做什么。”这只是情境假设，不能伪造为已收集的用户反馈。

我希望 AI 帮我推敲：这值得成为功能吗？普通 Note 能不能解决？是不是我给简单问题取了一个过大的名字？此时直接生成一份完整 PRD，会让格式的完整掩盖需求还没有论证。

### B2. 先查现状，再提方案

实际只读了 Mosaic 的 README、Attention handoff、Jump Palette 实现。当前本地已有 Note、Room 恢复与聚焦能力；Attention / MRU 运行态不应跨重启冒充当前状态。本地 checkout 与发布版本未逐项核对，因此稿里明确标记证据范围。

模拟请求：

> 根据这些资料，分开告诉我现有能力、这次提议、还缺证据的假设。然后比较普通 Note、给 Note 一个接续标记、独立 Checkpoint 三条路。

目前产品对“不得判断真伪”的约束容易被误解成 AI 不能辅助核对。应允许 AI 指出某项要求与给定资料冲突、缺了支持材料或版本对不上，并列出证据；不能把这变成一个“已验证为真”的徽章。

【待定建议】事实摘录、AI 提案、作者决定要在措辞与来历上分清，不必再添三种颜色。尤其 PRD 的“我们要做”必须来自作者认可，不能从助手措辞顺滑地漂进去。

### B3. 决定在不同章节之间发生

模拟 AI 提案：“离开 Room 时自动总结，返回时自动恢复。”

模拟作者取舍：“不要。退出弹窗打断人，自动总结会误解进度，恢复进程更是另一件事。我只要主动留一句话，自己决定什么时候跳转。”

这不是一个“已用回答”，而是一个带理由的决定。它会同时影响目标、非目标、交互、持久化和验收。若只挂在第一段，写到验收时便容易忘记；若只有 Stance 一句“不要自动”，又会丢掉为什么。

【待定建议】允许把作者认可的短结论留成“本篇决定”，带原讨论的返回路径。可用现有作者碎片 / 待决对象承载，不急着建完整决策系统。加入后续请求须作者明确指定；被否决的建议仍能找回，但不能当作当前要求。

这让 AI 的强大能力用在揭示代价和边界上，而不是替作者表决。

### B4. 写稿时发现自己原先没想清楚

作者先写：“点击继续即可恢复现场。”AI 追问：“目标 tile 被删了怎么办？恢复是切过去，还是重启进程？已读便笺算完成吗？”

作者意识到“恢复现场”承诺过大，将正文改成：“点击后聚焦关联对象；对象失效时保留留言并提示重新指定。”随后更新非目标与验收。

这里有价值的动作是：**找出受这次取舍影响的章节，给出修改候选和依据，作者逐处决定。** 所有候选仍在卡上，正文不自动改。不能要求 AI 永远只看当前段，然后由作者一个个发现它遗漏了什么。

【待定建议】在明确的“检查这次改动影响”请求中，作者授权读取全文或指定章节。一次审阅可以给一个主结果和可展开条目，再按需把具体问题挂到段旁。不用把每条都生成永久新卡，也不限制模型只能发起一次底层 API 调用才能完成工作。

### B5. 写成可讨论的 PRD，然后交付

完整演练稿见 [Mosaic · 下次从这里继续 · PRD](simulations/mosaic-resume-note-prd.md)，含问题、依据、方案比较、取舍、流程、异常、验收与未决项。

模拟最终请求：“按第一次接手这个需求的工程师读一遍，指出仍有两种实现解释的句子；不要替我宣称需求已经成立。”

PRD 中需要导出的，是选定方案、关键理由、边界和未决问题。外围探索不必全部交给读者，但**影响理解的理由不能永远藏在周围**。作者需要能从讨论选择一段理由整理进正文，或导出清楚的附录；不是把所有卡打包成另一个大仓库。

对于技术文章同理：读者最终看的是 Markdown 文章，不会看到作者桌面的漂亮连线。交付前需要一次“只看稿”的阅读，检查文章脱离卡片后是否仍讲得通。

## 四、我建议的产品理解

保留“纸在中间、产物先在旁边、作者决定正文”的骨架，但将实际工作扩成四个能反复往返的动作：**讨论问题、查看依据、作出取舍、组织表达。** 这不是四个模式页面，也不要求按顺序走。

### 1. 允许开题发生在正文之前【待定建议】

Topic 是当前这篇稿的边界。讨论可以关于整篇、章节或选定文字；不是所有思考都必须谎称来自一个已存在的段落。人可以先讨论，再决定文章想说什么。

这需要重新讨论产品 §6.4 与 AI 语义面 §四的段落锚定禁令；不是新增一个空字符串锚点来绕过它。

### 2. 支持有连续性的讨论，不强迫一问一张卡【待定建议】

卡片是把有价值的东西留下来的容器，不是每次模型输出必须完成的一道收纳手续。原始追问可折叠，作者提取结论；一个反例、一个引用、一个备选表达可以单独留下。

“不能做全局聊天软件”不等于“不能有局部连续对话”。写作主线始终在纸上，讨论围绕这篇；需要分支时再拆，不先让作者管理对话树。

### 3. 上下文按问题授权，减少让人管理模型的工作【待定建议】

“解释这句”默认局部；“比较这两节”附两节；“通读全文检查目标与验收”就是全文授权。发出前可用一行说明“本次阅读：全文 + 2 份资料”，可展开排除；不要求理解 progressive / curated / full。

已选材料在下一次作者发起请求时读取当前版本，不需要后台调用模型，也不必因改一个字就催“刷新包”。请求历史仍记录当时用了哪些版本。选择范围和固定历史快照是两件事，现文档把两者混在 `bodyHash / 包已旧` 里。

若问题要求的资料超出已授权范围，明示缺口；不能悄悄搜索其它 Topic 或读取其它文件。作者明确授权范围内的按需阅读，不应等同于未经手势的后台监视。

### 4. 作者的取舍要留下，而不只是 AI 的回答【待定建议】

可以留下“这篇从解析例子开始”“不做自动接续，因为不想误报进程状态”。AI 提出，作者接受、修改或拒绝；决定带理由，能回到讨论。不是自动把 AI 摘要变成作者 Stance。

同样应允许作者改变决定。旧决定仍是历史，不继续对新稿施加未标明的约束。

### 5. 围绕真实长内容工作【待定建议】

短卡适合提醒，一段解释、20 行代码、两列方案比较或一页文档需要更多阅读空间。可临时放大当前卡阅读，关掉回到同一写作位置；不用永久侧栏，也不必把纸和卡都压小。

显示归属、视觉留旁、送给模型的范围要分开。“我看着它写”不等于“每次问 AI 都带它”。看完也不自动算已用；拒绝一项方案也可能是有价值的产出。

### 6. 回来要恢复下一步，交付要脱离现场【待定建议】

恢复保留位置与展开卡，再允许作者留一句下一步。收尾提供作者主动的全文阅读 / 审阅，检查正文能否独立成立。两头都不需要后台 AI。

## 五、HTML 目前覆盖了什么，没覆盖什么

以下是源码审阅，不是已完成渲染测试。现有板很好地把纸和周围、落点、角色和回填选择拆开说明；问题是大多从“有一段话、有一张短卡”开始，作者最难的中间过程被省掉了。

| 文件 | 源码可确认的现状 | 对两个场景的影响 / 下一张板应表达的内容 |
| --- | --- | --- |
| `一次写作.html` | 开题后很快进入已有段落与短卡；旧 CSS 仍有彩色卡底与 22px 纸圆角 | 故事缺“没想清楚 → 连续讨论 → 自己选方向”，且不是最新视觉规范的单一真相 |
| `iPad横-写作现场.html` | 真实比例结构、段落滚动与卡归属；样本以短文本为主，纸是静态 article | 尚不能据此推断长代码、长回答、软键盘出现后的阅读与写作体验 |
| `ai-召唤球.html` | 主路径是拖把手到球，再选动词；普通旁注与请求多以 toast 演示 | 没有真实问题编辑、追问与取消 / 重试闭环；连续讨论每次从拖线开始会重，建议在卡内直接追问 |
| `ai-上下文与姿态.html` | 展示模式与“包已旧”；同屏是 Haskell 姿态与 Jump PRD 内容 | 会把上下文管理推给作者；也不能证明 Topic 切换隔离已成立。用完整单一场景替换混合占位材料 |
| `参考页卡.html` | 仿 Hoogle 的本地结果，非真实网页；刷新是改 URL 文本并提示，剪取显示预制卡；参考区宽 26% | 能说明概念，不能说明真实文档在窄栏可读、登录 / 失败 / 跳转 / 返回是否顺畅 |
| `回填选择.html` | 一句助手回答，footnote 按钮不检查来源；部分采用只提示待定，插入是显示固定 span | 缺少长内容选取、插入位置预览、撤销；无来源回答不该显示可成功引用。示意板的成功 toast 不能等于权限规则已实现 |

下一轮若改 HTML，我优先画 **一个完整可走的场景**：空纸提出问题 → 两次追问 → 保留依据和作者取舍 → 写一个真实段落 → 改掉它 → 对比审阅 → 留下一步。沿用现有纸与周围，不加一个新的工作台。无需先做另一批球、玻璃或入口布局。

## 六、需要重新讨论的文档约束

本表是异议登记，不是已生效规则。不能一边保持旧文标为已定，一边让实现默默按新想法走。

| 现有表述 | 本轮异议 | 建议讨论方向 |
| --- | --- | --- |
| “不写作时也有用，就不属于产品”（产品 §一） | 总结资料、解释例子在别处也有用，却是两种写作的必经过程；判据过宽 | 改问“是否服务于这篇稿的理解、判断或表达；结果能否回到该写作任务” |
| 无段落锚点就不能讨论（产品 §6.4，AI §2.2 / §四） | 把存储粒度当成人开始思考的前提 | Topic 级讨论也有明确归属；不用虚假空标题挂点 |
| 禁 `card.summarize / digest`（AI §2.3） | 禁止总结本身削弱助手；风险在伪造来源和自动替作者定稿 | 作者可要求比较 / 摘要，保留来源，产物仍在旁边，不自动变成决定或正文 |
| 所有加宽等作者先发现遗漏（AI §9.0） | 容易逼作者先识别 AI 没看见什么；全文审阅意图已是授权 | 根据这次明确任务选择范围，清楚显示；授权内按需读取，越界需作者选择 |
| 一手势等于一次请求（AI §六） | 强模型检索与读资料可能需要多个步骤，一次网络调用不是用户价值边界 | 讨论采用一次授权任务 + 有界成本 / 取消 / 进度；不等于立刻实现 agent 工具循环 |
| 卡片必须回到正文，未再展开的卡降权（产品 §3.5 / §十，AI §9.1） | 排除方向、得到理解、形成决定也能完成使命 | 不用插入率或打开次数替代认知价值；作者取舍和材料用途优先 |
| URL 实访使编造引用“无法构造”（数据 §五，AI §三） | 类型和 URL 字段只能限制结构，不能证明文本来自该页，更不能证明支持该论断 | 由实际检索 / 剪取通路构造来源记录，保留原始片段与位置；措辞别承诺真伪保证 |

另外，产品 §七的“重要文档自动跑”及 AI §2.4 的例外，与无定时器 / 无观察者地板冲突；产品 §七“直接生成正文段落不做”与允许候选片段的修订也容易误读。应分别明确作者主动整篇审阅，以及“生成候选”与“写入正文”的区别。本轮未把这些自行改成新定案。

## 七、按仓库五问记录（全部是模拟预测）

| 问题 | Traversable | Mosaic PRD |
| --- | --- | --- |
| 会在何时离开正文，为什么 | 尚无论点要讨论；查官方文档；去 GHC 运行例子 | 回仓库确认现状；比较普通 Note 是否已够用 |
| 哪些驻留能省一次切换 | 原始定义 + 自己的误解 + 反例输出 | 当前实现摘录 + 反对自动总结的理由 |
| 哪张创建后可能不再看 | 已帮助选定切口的开题候选，仍可能有价值 | 被排除的 Checkpoint 方案，理由应留下 |
| 哪张帮助隔天恢复 | “回来决定是否补列表例子，先别讲 Tree” | “方案选 Note 标记；还没决定入口与跨 Room 行为” |
| 哪些像为了产品而使用产品 | 先造标题才能问；每轮拉线；自己管理上下文包 | 每章重新勾相同约束；用已用/废弃替代“作者接受/拒绝及理由” |

此次模拟不能证明人一定会使用上述建议。它说明现有规则在哪些合理写作步骤上增加了额外仪式。下一轮讨论应围绕这些具体时刻，而不是按功能数量补全产品。
